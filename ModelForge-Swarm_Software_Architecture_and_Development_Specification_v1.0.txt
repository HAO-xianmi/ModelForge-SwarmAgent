1. EXECUTIVE SUMMARY
======================================================================

ModelForge-Swarm is an auditable, reproducible, and human-supervised
multi-agent platform for mathematical modeling workflows.

The system accepts:
    - A mathematical modeling problem statement
    - Optional PDF documents
    - Optional images
    - Optional spreadsheets
    - Optional CSV datasets
    - Optional competition rules
    - Optional user constraints
    - Optional prior research materials

The system produces:
    - A structured problem card
    - Domain analysis
    - Retrieved modeling methods
    - Multiple candidate modeling strategies
    - A structured critique report
    - Pilot experiment results
    - A selected or merged strategy
    - Data profiling reports
    - Executable code
    - Sandbox execution logs
    - Baseline comparisons
    - Robustness and sensitivity analyses
    - Evidence records
    - Verified citations
    - A report outline
    - A report draft
    - A LaTeX project
    - A PDF export
    - A reproducibility package
    - An AI-use disclosure record when required
    - A full audit trail

ModelForge-Swarm is not a collection of chatbots exchanging messages without
control. It is a stateful engineering system with explicit process stages,
well-defined responsibilities, structured outputs, deterministic services,
quality gates, bounded retry loops, and human approval points.

The core architectural decision is:

    Use a state machine and a shared blackboard as the system backbone.
    Use language-model agents only for tasks that require reasoning.
    Use deterministic services for tasks that must be reproducible.

The system combines two complementary ideas:

    1. A lightweight multi-agent swarm core:
       - Supervisor
       - Shared blackboard
       - Parallel modelers
       - Critic or judge
       - Code execution
       - Writer
       - Human checkpoints

    2. A stronger engineering layer:
       - Pilot experiments before final model selection
       - Experiment audit gates
       - Baseline enforcement
       - Robustness testing
       - Evidence registry
       - Citation verification
       - Competition compliance profiles
       - Reproducibility packaging
       - Benchmarking
       - Cost control
       - Observability

The result is a project that is realistic to implement, technically credible,
and suitable for GitHub presentation, research exploration, and portfolio use.

2. PRODUCT VISION
======================================================================

2.1 Vision Statement

ModelForge-Swarm aims to provide a disciplined computational workflow for
open-ended mathematical modeling tasks.

The system should help users answer the following questions:

    - What exactly is the problem asking?
    - What information is available?
    - What information is missing?
    - Which modeling methods are applicable?
    - Which candidate strategy is most defensible?
    - Which strategy works best in actual experiments?
    - Can the code run successfully?
    - Are the results reproducible?
    - Are the conclusions supported by evidence?
    - Are citations real and relevant?
    - Are the outputs compliant with the selected operating mode?
    - Which decisions were made automatically?
    - Which decisions were confirmed by a human?

2.2 Product Value

The project is designed to demonstrate competence in:
    - Multi-agent systems
    - Workflow orchestration
    - State machine design
    - Structured LLM outputs
    - Tool-using agents
    - Code sandboxing
    - Data science experimentation
    - Experiment reproducibility
    - Retrieval-augmented generation
    - Evidence-grounded generation
    - Prompt engineering
    - Full-stack product engineering
    - Security boundaries
    - Cost-aware AI application design
    - Benchmarking and evaluation

2.3 Public Product Message

Recommended short description:

    ModelForge-Swarm is an auditable multi-agent copilot for mathematical
    modeling. It parses problem statements, explores multiple strategies,
    runs reproducible experiments in a sandbox, validates evidence, and
    generates structured report drafts with human approval checkpoints.

Recommended tagline:

    From problem statement to reproducible modeling workflow.

The platform MAY later support:

    - Promise competition awards
    - Generate fabricated experimental values
    - Treat unexecuted code as validated code

    - Execute arbitrary code without resource limits

4. DESIGN PRINCIPLES
======================================================================

4.1 Explicit State Over Free Conversation

Agents MUST exchange information through structured state updates and
versioned artifacts.

Agents SHOULD NOT depend on long conversational histories.

Every important decision MUST be representable as:
    - An input state
    - A named operation
    - A structured output
    - A state transition
    - A traceable artifact or event

4.2 Standard Operating Procedure Before Prompt Design

The engineering order MUST be:
    1. Define the workflow
    2. Define state fields
    3. Define component boundaries
    4. Define input and output schemas
    5. Define quality gates
    6. Define failure paths
    7. Define prompts
    8. Implement model routing

4.3 Experiments Before Final Decisions

The system MUST NOT select a final strategy solely from textual arguments when
a low-cost experiment is feasible.

At least one pilot experiment SHOULD be run for each viable candidate
strategy.

4.4 Evidence Before Writing

Quantitative claims in the final report MUST be linked to evidence.

A report-writing agent MUST NOT invent:
    - Metrics
    - Table values
    - Chart values
    - Experimental outcomes
    - Citation metadata
    - Model comparison results

4.5 Deterministic Services for Deterministic Work

The following tasks SHOULD be implemented as deterministic services rather
than LLM agents:
    - File hashing
    - Dependency locking
    - Dataset profiling
    - Artifact storage
    - Citation metadata checks
    - PDF compilation
    - Resource accounting
    - Sandbox timeout control
    - Random seed recording

4.6 Bounded Autonomy

Every loop MUST have:
    - A maximum retry count
    - A timeout
    - A budget limit
    - An escalation path
    - A human-visible failure record

4.7 Recovery by Design

Long-running workflows MUST support:
    - Persistent state
    - Resume after interruption
    - Human review
    - Partial re-execution
    - Artifact reuse
    - Stage-level rollback

4.8 Explainability by Default

Every selected strategy MUST include:
    - Selection rationale
    - Rejected alternatives
    - Major assumptions
    - Risks
    - Required experiments
    - Known limitations

5. OPERATING MODES
======================================================================

5.1 Practice Mode

Purpose:
    Training, learning, public-problem replay, and personal experimentation.

Behavior:
    - Full automation MAY be enabled.
    - Report drafting MAY be fully enabled.
    - Automatic strategy generation MAY be enabled.
    - Automatic code generation MAY be enabled.
    - Automatic report export MAY be enabled.
    - All audit logs MUST still be preserved.

5.2 Contest-Compliant Mode

Purpose:
    Assistance during a real competition, subject to the rules of that
    competition.

Behavior:
    - A competition profile MUST be loaded.
    - Human approval checkpoints MUST be enabled.
    - AI-use records MUST be preserved.
    - Restricted actions MUST be disabled according to the profile.
    - The system MUST clearly separate suggestions from human-confirmed work.
    - The system MUST export an AI disclosure package when required.
    - The user MUST remain responsible for final submission decisions.

5.3 Research Mode

Purpose:
    Benchmarking, model comparisons, workflow experiments, and academic
    evaluation.

Behavior:
    - Full decision traces MUST be recorded.
    - Model identifiers MUST be recorded.
    - Prompt versions MUST be recorded.
    - Token usage MUST be recorded.
    - Latency MUST be recorded.
    - Cost estimates MUST be recorded.
    - Ablation settings MUST be recorded.
    - Human-review scores MAY be attached.

5.4 Mode Selection Rule

A run MUST have exactly one active mode.

Mode changes after execution begins SHOULD require:
    - Explicit user confirmation
    - A new audit event
    - Revalidation of enabled tools
    - Revalidation of checkpoints

6.3 Architectural Boundaries

Boundary A: Agent-to-Agent
    Agents MUST exchange structured artifacts through the blackboard.
    Free-form debate MAY occur only inside a bounded debate step and MUST be
    summarized into a structured output.

Boundary B: Agent-to-Tool
    Each agent MUST receive only the minimum tool permissions required.

Boundary C: Writer-to-Evidence
    Report-writing agents MUST only use claims that are registered and marked
    as verified.

Boundary D: Sandbox-to-Host
    Sandbox code MUST be isolated from host credentials, host files outside
    the mounted workspace, and unrestricted network access.

Boundary E: Contest Mode
    Tools, agents, and export actions MUST be governed by the active
    competition profile.

7. CONTROL PLANE
======================================================================

7.1 Supervisor

Type:
    Deterministic workflow controller

Responsibilities:
    - Start runs
    - Load configuration
    - Initialize blackboard state
    - Select the next node
    - Enforce transition rules
    - Limit retries
    - Enforce budgets
    - Pause at checkpoints
    - Resume runs
    - Mark runs as completed, failed, or cancelled

The Supervisor MUST NOT:
    - Generate modeling strategies
    - Invent experimental conclusions
    - Write report paragraphs
    - Bypass failed quality gates
    - Bypass required human checkpoints

7.2 Checkpoint Manager

Responsibilities:
    - Create pending checkpoint records
    - Persist checkpoint context
    - Notify the interface layer
    - Accept human approval
    - Accept human modifications
    - Accept rejection and rollback instructions
    - Record actor, timestamp, and decision

Checkpoint decisions:
    - APPROVE
    - APPROVE_WITH_EDITS
    - REJECT_AND_RETRY
    - RETURN_TO_STAGE
    - CANCEL_RUN

7.3 Budget Manager

Responsibilities:
    - Track LLM token usage
    - Track estimated provider cost
    - Track sandbox runtime
    - Track retry counts
    - Track file sizes
    - Enforce hard limits
    - Emit warning events
    - Stop runs when limits are exceeded

Recommended default limits for MVP:
    - Strategy proposer instances: 3
    - Debate rounds: 2
    - Debug retries per script: 3
    - Sandbox runtime per execution: 120 seconds
    - Maximum active experiment variants: 20
    - Maximum input bundle size: configurable
    - Maximum total run duration: configurable

7.4 Policy Guard

Responsibilities:
    - Read the operating mode
    - Read the competition profile
    - Determine allowed tools
    - Determine allowed agent actions
    - Determine required checkpoints
    - Determine required disclosure records
    - Reject prohibited transitions

7.5 Run Coordinator

Responsibilities:
    - Assign run identifiers
    - Create run directories
    - Create initial database records
    - Queue long tasks
    - Collect completion events
    - Persist run summaries

8. REASONING AGENT CATALOG
======================================================================

The MVP SHOULD use ten reasoning agent classes. Three strategy proposers SHOULD
run in parallel as separate instances of the same class.

8.1 ProblemParserAgent

Purpose:
    Convert raw input documents into a structured problem card.

Inputs:
    - Problem statement text
    - Parsed PDF text
    - Extracted tables
    - Image descriptions if available
    - File metadata
    - Active operating mode
    - Competition profile

Outputs:
    - problem_card.json
    - parsing_notes.json
    - missing_information.json

Required output fields:
    - title
    - problem_summary
    - subproblems
    - objectives
    - decision_variables
    - constraints
    - datasets
    - required_outputs
    - formatting_requirements
    - ambiguities
    - missing_information
    - confidence
    - source_references

Invariant:
    Each extracted requirement MUST include a source reference.

Failure conditions:
    - Missing required statement text
    - Unreadable file
    - Ambiguity that prevents safe continuation
    - Unsupported file type

8.2 DomainAnalystAgent

Purpose:
    Identify relevant domain concepts, modeling families, and risks.

Inputs:
    - problem_card.json
    - available datasets
    - optional user context

Outputs:
    - domain_analysis.json

Required output fields:
    - domain_tags
    - likely_problem_families
    - domain_assumptions
    - key_terms
    - data_requirements
    - potential_external_facts
    - research_questions
    - risks
    - recommended_specialists

Invariant:
    The agent MUST distinguish facts from assumptions.

8.3 MethodRetrieverAgent

Purpose:
    Retrieve candidate modeling methods from a structured method library.

Inputs:
    - problem_card.json
    - domain_analysis.json
    - method library
    - optional case library

Outputs:
    - retrieved_methods.json

Each method record MUST include:
    - method_id
    - name
    - category
    - suitability_score
    - applicability_conditions
    - assumptions
    - required_data
    - advantages
    - limitations
    - computational_cost
    - implementation_templates
    - recommended_metrics
    - common_failure_modes
    - reference_ids

Invariant:
    Retrieved methods MUST come from registered library entries.

8.4 StrategyProposerAgent

Purpose:
    Generate complete modeling strategies.

Instances:
    - interpretability_first
    - performance_first
    - innovation_first

Optional fourth instance:
    - low_cost_first

Inputs:
    - problem_card.json
    - domain_analysis.json
    - retrieved_methods.json
    - resource limits
    - competition profile

Outputs:
    - strategy_candidate_{id}.json

Each strategy MUST include:
    - strategy_id
    - strategy_name
    - design_goal
    - subproblem_mapping
    - method_stack
    - assumptions
    - variable_definitions
    - mathematical_formulation
    - data_requirements
    - preprocessing_plan
    - experiment_plan
    - baseline_plan
    - robustness_plan
    - visualization_plan
    - expected_artifacts
    - estimated_runtime
    - implementation_risk
    - known_limitations
    - fallback_plan

Invariant:
    The candidate MUST define a runnable pilot experiment.

8.5 SkepticAgent

Purpose:
    Challenge each proposed strategy.

Inputs:
    - strategy candidates
    - problem card
    - dataset profile if available
    - resource limits

Outputs:
    - skeptic_report.json

Checks:
    - Weak assumptions
    - Missing constraints
    - Misaligned objective functions
    - Overfitting risks
    - Data leakage risks
    - Unsupported complexity
    - Missing baseline
    - Missing validation plan
    - Runtime risks
    - Reportability risks
    - Compliance risks

Output per candidate:
    - severity-ranked issues
    - required fixes
    - optional improvements
    - pilot experiment objections
    - pass or revise recommendation

Invariant:
    SkepticAgent MUST NOT silently approve every strategy.

8.6 StrategyJudgeAgent

Purpose:
    Select, merge, or reject candidate strategies.

Inputs:
    - strategy candidates
    - skeptic report
    - pilot experiment results
    - resource limits
    - user edits from checkpoint if any

Outputs:
    - selected_strategy.json
    - strategy_decision_record.json

Allowed decisions:
    - SELECT
    - MERGE
    - REVISE
    - REGENERATE
    - ESCALATE_TO_HUMAN

Scoring dimensions:
    - Problem fit
    - Data fit
    - Feasibility
    - Interpretability
    - Experimental evidence
    - Robustness potential
    - Novelty
    - Runtime cost
    - Report quality potential
    - Compliance

Invariant:
    The decision MUST reference actual pilot experiment evidence when available.

8.7 CodeAuthorAgent

Purpose:
    Generate executable implementation code.

Inputs:
    - selected strategy
    - dataset metadata
    - data profile
    - code templates
    - sandbox limits

Outputs:
    - scripts/
    - notebooks/
    - requirements.lock or environment specification
    - run_manifest.json

Requirements:
    - Use deterministic random seeds where applicable
    - Save outputs to defined paths
    - Emit machine-readable metrics
    - Avoid hidden dependencies
    - Avoid unrestricted network calls
    - Separate preprocessing, modeling, evaluation, and plotting

Invariant:
    Every quantitative report artifact MUST be generated by executable code.

8.8 DebuggerAgent

Purpose:
    Repair code execution failures with minimal changes.

Inputs:
    - source code
    - traceback
    - stdout
    - stderr
    - dependency metadata
    - retry history

Outputs:
    - patch
    - debug explanation
    - updated code
    - debug_patch_log.jsonl

Rules:
    - Prefer minimal patches
    - Do not rewrite the entire project unless required
    - Do not disable validation checks to force success
    - Do not fabricate outputs
    - Respect maximum retries

Invariant:
    Each patch MUST record the reason for the change.

8.9 PaperArchitectAgent

Purpose:
    Design the report outline before drafting prose.

Inputs:
    - verified claims
    - figures
    - tables
    - selected strategy
    - citations
    - competition template
    - required sections

Outputs:
    - report_outline.json

Each section record MUST include:
    - section_id
    - title
    - purpose
    - required_claim_ids
    - required_figure_ids
    - required_table_ids
    - required_citation_ids
    - word_budget
    - human_review_required

Invariant:
    No section may request unsupported claims.

8.10 PaperWriterAgent

Purpose:
    Draft evidence-grounded report text.

Inputs:
    - report outline
    - verified claims
    - figures
    - tables
    - verified citations
    - template constraints
    - style guide

Outputs:
    - report.md
    - report.tex
    - report_claim_map.json

Rules:
    - Every quantitative claim MUST cite a claim_id
    - Every figure mention MUST cite a figure_id
    - Every table mention MUST cite a table_id
    - Every literature statement MUST cite a citation_id
    - Unsupported claims MUST be omitted or explicitly marked for human review

Invariant:
    The writer MUST NOT add new experimental values.

    - Updated risk assessment

21. BASELINES, ROBUSTNESS TESTING, AND EXPERIMENT AUDITING
======================================================================

21.1 Baseline Requirement

Each final strategy MUST include at least one baseline unless:
    - No meaningful baseline exists
    - A human reviewer approves the waiver
    - The waiver is recorded

Examples:
    Prediction:
        Mean predictor
        Moving average
        Linear regression
        ARIMA

    Optimization:
        Greedy heuristic
        Random feasible solution
        Simple rule-based allocation

    Classification:
        Majority class
        Logistic regression
        Decision tree

21.2 Robustness Tests

Recommended default tests:
    - Parameter perturbation: +/-5%, +/-10%, +/-20%
    - Repeated seeds
    - Data subsampling
    - Extreme-case scenarios
    - Missing-data scenarios
    - Noise injection
    - Constraint stress tests
    - Ablation experiments

21.3 Experiment Auditor

The audit MUST check:
    - Code executed successfully
    - Random seed recorded
    - Input hashes recorded
    - Dependencies recorded
    - Train-test separation exists where required
    - Data leakage checks passed
    - Baseline exists or waiver exists
    - Robustness tests exist or waiver exists
    - Metrics align with objectives
    - Figures are linked to scripts
    - Tables are linked to scripts
    - Claims are evidence-backed

21.4 Blocking Issues

Examples of blocking issues:
    - Unexecuted code
    - Missing train-test split for predictive modeling
    - Data leakage
    - Missing baseline without waiver
    - Fabricated or manually typed metrics
    - Missing input hashes
    - Missing reproducibility metadata
    - Unsupported report claims

30. SECURITY MODEL
======================================================================

30.1 Threat Model

Potential threats:
    - Malicious uploaded files
    - Malicious generated code
    - Sandbox escape attempts
    - Secret leakage
    - Unrestricted network access
    - Excessive resource consumption
    - Prompt injection in documents
    - Unsafe file paths
    - Oversized input bundles
    - Dependency abuse

30.2 Required Controls

The system MUST:
    - Sanitize filenames
    - Validate MIME types
    - Limit file sizes
    - Store uploads outside executable paths
    - Use non-root sandbox users
    - Deny host secret mounts
    - Restrict outbound network access
    - Restrict CPU
    - Restrict memory
    - Restrict runtime
    - Restrict disk usage
    - Capture logs
    - Preserve audit records
    - Validate output paths
    - Reject path traversal
    - Separate system prompts from document content

30.3 Prompt Injection Defense

Document content MUST be treated as untrusted data.

Agents MUST NOT follow instructions embedded in problem documents unless the
instructions are part of the recognized problem statement or competition
rules.

The parser SHOULD separate:
    - User instructions
    - Competition rules
    - Problem content
    - External document content
    - Tool outputs

32.2 Retry Policy

Recommended defaults:
    - Model-provider transient retry: 2
    - Parser retry: 1
    - Code debug retry: 3
    - Citation metadata retry: 2
    - LaTeX compilation retry: 2
    - Sandbox infrastructure retry: 1

32.3 Escalation Policy

After retry exhaustion:
    - Persist state
    - Mark the stage as blocked
    - Create a human-review checkpoint
    - Provide error summary
    - Provide logs
    - Provide recommended next actions

32.4 Resume Policy

A resumed run MUST:
    - Load the latest validated state version
    - Verify artifact availability
    - Verify profile version
    - Recompute pending transitions
    - Preserve the prior audit history

33.1 Cost Drivers

Major cost drivers:
    - Number of proposer instances
    - Number of debate rounds
    - Prompt size
    - Dataset-summary size
    - Code-debug loops
    - Citation retrieval
    - Report length
    - Sandbox runtime
    - Number of robustness experiments

33.2 Optimization Techniques

The system SHOULD:
    - Use cheaper models for parsing
    - Use stronger models for strategy judgment
    - Use coding-focused models for code generation
    - Compress state before LLM calls
    - Reference artifacts instead of embedding full files
    - Cache method retrieval
    - Cache citations
    - Limit debate rounds
    - Stop failed strategies early
    - Use pilot experiments before full experiments
    - Batch robustness runs where feasible

33.3 Budget Profiles

Recommended budget profiles:
    - demo
    - standard
    - high_quality
    - research

Each profile SHOULD configure:
    - model routing
    - proposer count
    - retry counts
    - sandbox timeout
    - robustness variants
    - report length
    - citation depth

41. ACCEPTANCE CRITERIA
======================================================================

41.1 MVP Acceptance Criteria

The MVP is accepted when:
    1. A user can create a run.
    2. A user can upload a text or PDF problem.
    3. The parser produces a structured problem card.
    4. The system generates at least three candidate strategies.
    5. The system critiques the candidates.
    6. The system selects one strategy.
    7. The system generates executable Python code.
    8. Docker executes the code.
    9. Logs are captured.
    10. At least one result artifact is registered.
    11. A markdown report draft is generated.
    12. The run directory contains a manifest.

41.2 Portfolio-Grade Acceptance Criteria

The portfolio-grade release is accepted when:
    1. Human checkpoints work.
    2. Pilot experiments work.
    3. Automatic debugging works with bounded retries.
    4. Baseline comparisons work.
    5. Robustness tests work.
    6. Evidence claims link to artifacts.
    7. Report claims map to evidence.
    8. LaTeX export works.
    9. PDF export works.
    10. ZIP reproducibility export works.
    11. Web console works.
    12. Audit events are visible.
    13. Cost and runtime summaries are visible.
    14. Three example problems are documented.

41.3 Research-Grade Acceptance Criteria

The research-grade release is accepted when:
    1. Benchmark suite contains at least 15 public problems.
    2. Evaluation metrics are computed automatically.
    3. Ablation studies can be reproduced.
    4. Model-provider comparisons are supported.
    5. Prompt versions are tracked.
    6. Competition profiles are versioned.
    7. Citation verification is supported.
    8. Security tests pass.
    9. Deployment documentation is complete.
    10. Public benchmark report is generated.

    snake_case

Classes:
    PascalCase

API paths:
    kebab-case where appropriate

Artifact IDs:
    artifact_{type}_{uuid}

Experiment IDs:
    experiment_{uuid}

Run IDs:
    run_{timestamp}_{short_uuid}

Claim IDs:
    claim_{uuid}

G.2 Versioning

Use semantic versioning:
    MAJOR.MINOR.PATCH

Version:
    Prompt templates
    Competition profiles
    Method-library entries
    API schema
    Database migrations
    Sandbox images

G.3 Documentation

Every major module SHOULD include:
    - Purpose
    - Inputs
    - Outputs
    - Invariants
    - Failure modes
    - Tests
    - Security notes

G.4 Open-Source README Checklist

The public README SHOULD include:
    - Project summary
    - Architecture diagram
    - Workflow diagram
    - Demo GIF
    - Quick start
    - Feature list
    - Example run
    - Export structure
    - Security notes
    - Compliance positioning
    - Benchmark results
    - Roadmap
    - Contribution guide
    - License
